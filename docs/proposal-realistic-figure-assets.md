# Proposal — realistic figure assets for the pose library

**Status: ADOPTED 10 August 2026 as PRD §11 v1.7.** The owner chose the **Blender Studio
Human Base Meshes** (CC0). PRD §9 item 1 is closed. Read `PRD.md` §11 v1.7 for the
authoritative text — it supersedes this document wherever the two differ, and they differ in
several places: the draft amendment below is numbered v1.4 (stale), covers three poses rather
than four, and its "feasibility in the current dev container" section describes the *agent's*
container, not the owner's Mac, where Blender 5.2 LTS is installed and the pipeline was
spiked successfully on 10 August. This file is kept as the analysis and the argument, not as
a specification.

Raised 7 August 2026 by the owner, with a reference image: a three-view render of a
sculpted anatomical human base mesh (Daz Genesis / MakeHuman class — real shoulder,
clavicle, knee and facial anatomy, matte grey, tens of thousands of polygons), and the
requirement *"I need at least this level of realism."*

## The honest problem statement

The pose library today is `scripts/generate-pose-glbs.mjs`: capsules, boxes, spheres and
cones assembled in Three.js and exported per pose. The facial landmarks added the same day
(brow ridge, nose, cheekbones) are the ceiling of that approach, not a step toward the
reference. **The gap is a different asset class, not a tuning problem.** No arrangement of
primitives in a generator script reaches a sculpted base mesh; the geometry in the
reference was modelled by a person (or scanned), and the only way to have it is to obtain
it.

What that changes, concretely:

| | today | reference-class figure |
| --- | --- | --- |
| source | generated by a 190-line script | authored/scanned asset, licensed |
| triangles per pose | ~5k | 20k–60k typical |
| `.glb` size per pose | ~94 KB | ~1–5 MB |
| adding a pose | edit `POSES` table, re-run | rig + pose in a DCC tool, re-export |
| in git | trivial | ~5–15 MB for three poses |

## What it does *not* require

**No app code changes.** This is the payoff of PRD §4: a character's `mesh` is
`{kind:'gltf', path}` and `buildObject()` is the only code that knows the difference. §11
v1.2 already says so in as many words — *"a Mixamo or MakeHuman figure exported per-pose to
`.glb` drops into the same folder under the same contract."* No schema change, no parser
change, no `Viewport.tsx` change, no `.myo` envelope change. `poses.json` gains rows; the
files land in `public/assets/poses/`.

The one thing that *would* change is `scripts/generate-pose-glbs.mjs`'s role: it stops
being the source of the library and becomes either dead code or a fallback generator for
placeholder poses. That is a call to make when the assets land, not before.

## What it does require

1. **An asset and a licence.** The realistic options and their catch:
   - **Daz Genesis base figures** — free to use, but the EULA governs redistribution;
     committing a derived `.glb` to a repo (even a private one) needs the licence read
     properly first. Closest match to the reference image.
   - **MakeHuman / MPFB2** — output is CC0. Anatomically credible, below Daz in fidelity,
     no redistribution problem at all. **The recommended starting point.**
   - **Blender Studio Human Base Meshes** — CC0, clean topology, unrigged.
   - **Mixamo** — rigged and posed characters, but Adobe account required, stylised rather
     than anatomical, and the licence again needs reading before anything is committed.
2. **A posing tool.** The three poses are `standing`, `sitting`, `crouching`. A base mesh
   arrives in one rest pose; producing the other two needs a rig and a DCC tool — realistically
   headless Blender driven by a script (`bpy`), checked into `scripts/` so the library stays
   reproducible rather than a one-off manual export.
3. **A decision on where the assets live.** Three multi-megabyte binaries per figure variant
   in git, or an asset directory outside the repo with a fetch script. Git LFS is a third
   option and a new dependency.

### Feasibility in the current dev container (checked, 7 Aug 2026)

- `blender` is **not installed**; `bpy` is not importable. `apt-get install -s blender`
  resolves, and pypi.org is reachable, so `pip install bpy` is *plausible* (~300 MB) but
  unproven here.
- `download.blender.org` and `github.com` are **not reachable** through the agent proxy
  (000 and 400 respectively), so fetching a base mesh from upstream currently fails. The
  asset would have to be added to the repo by the owner, or the proxy allow-list widened.

That is the practical blocker: the tooling is probably installable, the asset currently is
not fetchable.

## The scope question the owner has to answer

PRD §11 v1.1 states, as standing fact, that *"every object is still proxy geometry"*, and
§11's governing rule exists to stop "it would help the director see it" from justifying
each next step toward photorealism. A reference-class human figure does not obviously
violate the rule — the rule is about **rendering features** (ray tracing, PBR, bloom, AO),
and this changes **an asset**, with no shading change whatsoever. But it does contradict
the plain sentence quoted above, and it is the kind of change §11 exists to make
deliberate. Hence: amendment, not a quiet swap.

Argument for, in the tool's own terms: a proxy capsule cannot tell a director which way a
figure's shoulders are turned, where the eyeline goes, or whether a shot reads as a
two-shot or a stand-off. Those are blocking questions, and body language answers them. That
is a stronger case than "it looks better."

Argument against, recorded honestly: the tool's value is speed and legibility. A 60k-triangle
figure per character multiplies scene cost, and per-pose assets that must be produced in
Blender make "add a pose" a modelling task instead of a five-line table edit — the exact
property §11 v1.2 was proud of. Non-goal #7 (no rigging, no morphs, no expressions) still
stands either way: the assets stay static per-pose exports.

## Draft amendment text — for the owner to adopt, edit, or discard

> ### v1.4 — <date>: realistic figure assets
>
> **Requested by the owner on 7 August 2026**, with a reference render of a sculpted
> anatomical base mesh: proxy capsules and the primitive mannequin do not carry enough body
> language to read blocking, and the owner requires figure geometry of at least that
> standard.
>
> **What changed in this document**
>
> - **§9 item 1 (asset pipeline) closes** in favour of `<chosen source>`. All other §9
>   items stand.
> - **§11 v1.1's "every object is still proxy geometry" is narrowed**: characters carry
>   authored figure meshes; props, environment and every other object remain proxy geometry.
> - **No schema change, no parser change, no `.myo` change** — by construction, per §4.
>
> **Authorized to build under this amendment**
>
> 1. A reproducible asset pipeline in `scripts/`: import the licensed base mesh, apply each
>    pose in the library, export `.glb` to `public/assets/poses/`.
> 2. Replacement of the three existing pose meshes with figure-based ones, `poses.json`
>    unchanged in shape.
> 3. A recorded decision on asset storage (in-repo, LFS, or fetched).
>
> **Still out, and unaffected:** rigging, IK, pose editors, morphs, facial expression and
> animation (non-goals #6 and #7 stand — the assets are static per-pose exports). Every
> rendering-scope item on §11's out-list stays out; this amendment changes geometry, never
> shading.
>
> **Acceptance**
>
> - [ ] A scene renders the three poses as figure meshes with no code change outside the
>       asset pipeline script.
> - [ ] Adding a fourth pose is a documented, repeatable procedure.
> - [ ] `npx tsc --noEmit`, `npm run test:ci` and `CI=true npm run build` stay green, and
>       `poses.test.ts` still ties `poses.json` to real files on disk.

## Recommended next step

Pick the source (MakeHuman/MPFB2 if licence simplicity matters, Daz if fidelity does), drop
one base mesh into the repo or open the proxy to fetch one, and the pipeline script plus the
three re-exported poses is a contained piece of work from there.
