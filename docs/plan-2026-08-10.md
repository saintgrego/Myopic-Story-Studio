## 2. Issues to resolve (morning)

### 2.1 Pose base-anchoring is broken across all four poses — **the real bug**

STATE.md flagged this on 9 Aug and left it for "a library-wide pass". Re-measured from the
committed `.glb` files via `GLTFLoader` + `Box3` under plain Node:

| pose | `minY` | verdict |
| --- | --- | --- |
| standing | **−0.0398** | sinks 4.0 cm **into** the floor |
| sitting | +0.0302 | floats 3.0 cm |
| crouching | +0.0539 | floats 5.4 cm |
| lying | +0.0268 | floats 2.7 cm |

**All 12 prop proxies measure `0.0000`.** The convention is intact everywhere except the
pose library, which isolates the cause cleanly: the `POSES` table's `hipY` values were
eyeballed against the *old capsule* mannequin, and the 7 Aug body rebuild changed the leg
segment and foot geometry underneath them. `lying`'s `rootLift: 0.15` was likewise tuned to
the old torso radius.

**Fix: derive the offset, don't re-eyeball it.** Re-tuning four constants by hand is exactly
what produced the drift, and it would drift again on the next mannequin change. Instead, in
`buildFigure()`/the export step: compute the assembled figure's `Box3` and translate the root
so `minY === 0` before export. `rootLift` is subsumed by this and comes out of the `POSES`
table; `hipY` stays, but stops being load-bearing for floor contact.

- Watch for: this changes **all four binaries**, shifting rendered figures by up to 5.4 cm.
  That shift *is* the correction, but it means the gel-filter milestone's byte-identical
  screenshot baselines no longer apply to poses. Expected, not a regression.
- Not affected: `window`'s sill-height exception is a **prop** rule (`props.json`), untouched
  by an auto-ground pass over poses.

### 2.2 `poses.test.ts` cannot detect a stale or ungrounded binary

The same gap twice over: it let `lying.glb` sit at 87 KB beside three 156 KB siblings, and it
is silent on every number in the table above. It checks that `poses.json` and the files
*correspond by name*, nothing about the files themselves.

**Add a convention test, not a byte-equality test:** assert every pose `.glb` loads and its
`Box3.min.y` is within ~1 mm of 0. That single assertion would have caught the stale binary
*and* the anchoring bug, and it encodes the base-anchored rule rather than freezing a hash.

  into the gates rather than forcing it into the suite.

## 3. Why the anchoring fix goes before Blender

The mannequin may be replaced tomorrow afternoon, so fixing it first looks like wasted work.
It isn't, for three reasons:

1. **It builds the acceptance harness.** "Is this figure grounded and facing +Z?" is exactly
   the question every Blender export has to answer, and 2.1/2.2 produce the measurement code
   that answers it. Doing Blender first means importing figures with no way to prove they
   landed correctly.
2. **The proxy generator survives either way.** The proposal itself says it becomes "a
   fallback generator for placeholder poses" — a fallback that puts figures 5 cm off the
   floor is not a fallback.
3. **The afternoon has a licence fork in it** (§4.3). If the source decision stalls, you end
   the day with a *fixed* pose library rather than a broken one plus an unfinished pipeline.

## 4. Connecting Blender (afternoon)

### 4.0 What this is

A reproducible pipeline in `scripts/` that imports a licensed base mesh, applies each pose in
the library, and exports `.glb` into `public/assets/poses/` — replacing the procedural
mannequin with authored figure geometry.

**No app code changes. By construction.** This is the payoff of PRD §4: `poses.json` gains
nothing but new content behind the same paths, `buildObject()` is untouched, the parser is
untouched, the `.myo` envelope is untouched. Confirmed in the code: `Viewport.tsx:28`'s
`LIBRARY_PATHS` already re-materials anything listed in `poses.json` from the warm-grey
palette, so new figures pick up the palette automatically and any authored skin texture they
arrive with is discarded — which is what PRD §11 requires anyway (no texture maps).

### 4.1 Amendment before code — and it is **v1.7**, not v1.4

PRD §11 requires the amendment logged first. `docs/proposal-realistic-figure-assets.md` has
ready-to-adopt text, but it is drafted as **v1.4** — stale. `main`'s §11 is at **v1.6** (gel
filters, 8 Aug). Per STATE.md's own hard-won rule: *fetch `main` and read §11's last heading
immediately before writing the amendment, and renumber as the last step.* So it lands as
**v1.7**, and §9 item 1 closes with it.

### 4.2 Pipeline shape

- **Drive the Blender binary, do not `pip install bpy`.** The system `python3` has no `bpy`
  and does not need one — `/Applications/Blender.app/Contents/MacOS/Blender --background
  --factory-startup --python <script>` works today and pins the Python to Blender's own
  3.13.13. `--factory-startup` keeps a personal Blender config from changing the output.
- **`scripts/blender/build-pose-glbs.py`**, plus a thin wrapper so the ergonomics match the
  existing `node scripts/generate-pose-glbs.mjs`.
- **Base mesh lives in `assets-src/`**, gitignored at first, so the storage question
  (in-repo / LFS / fetched — proposal item 3) is answerable *after* seeing the real file
  sizes rather than guessed at now.
- **`src/poses.json` shape does not change.** Same four names, same four paths.

### 4.3 The fork: source decision, made at the spike, not before

Run the spike **source-agnostic** — get *any* mesh (even Blender's default cube, then a
Suzanne) through headless → `.glb` → into the viewport, with orientation and grounding
verified. That is ~90 minutes and it de-risks everything mechanical. Only then pick:

| source | licence | rig | note |
| --- | --- | --- | --- |
| Blender Studio base meshes | CC0, no question | none (Rigify present) | cleanest licence story |
| MakeHuman / MPFB2 | CC0 | rigged | needs MPFB2 added to Blender first |
| Daz Genesis | **EULA governs redistribution** | rigged | closest to your reference render; read the licence before anything is committed |

Deciding here rather than up front costs nothing, because everything before the fork is
identical for all three.

### 4.4 The landmine to expect

**Axis convention.** The mannequin faces **+Z** (the nose marker), and every pose, the
parser's rotation guidance, and the prop proxies all assume it. Blender's glTF exporter
defaults to `+Y up, -Z forward`. Get this wrong and figures arrive facing backwards or on
their side, which reads as a posing bug rather than an export-flag bug and will burn an hour.
Verify with the §2.2 harness on the very first export, before posing anything.

Second-order: 1–5 MB per pose against ~156 KB today. Four poses ≈ up to 20 MB. Not a
blocker, but it is what makes 4.2's storage question real.
